Contributing to Friday Night Funkin' is open to everyone — whether you're filing a bug report, suggesting an improvement, fixing a typo in the docs, or submitting a pull request with code changes. This guide walks through every type of contribution and the expectations around each so your work has the best chance of being reviewed and merged.

## Part 1: Etiquette

Good contributions start with good communication. Keep these principles in mind whenever you open an issue or pull request:

- **Be respectful.** Everyone here is trying to help improve the game. Treat others the way you'd want to be treated.
- **Write clear, concise titles.** Don't put your entire description in the title field — save the details for the body.
- **Don't spam.** Avoid opening duplicate issues or unnecessary pull requests.
- **Use common sense.** If something feels off, it probably is. When in doubt, check existing issues and discussions first.

## Part 2: Issues

Issues serve many purposes, from reporting bugs to suggesting new features. Before you open one, make sure you meet all the requirements below.

### Requirements

Make sure you're playing:

- The **latest version** of the game (currently **v0.8.6**, or **v0.8.7** for Android), or a public playtest version (v0.9 Feature Preview builds)
- **Without any mods** (unless the issue specifically involves mod behavior)
- On [Newgrounds](https://www.newgrounds.com/portal/view/770371) or downloaded from [itch.io](https://ninja-muffin24.itch.io/funkin) — only official builds are supported

### Issue Types

Choose the template that best matches your situation:

  <Accordion title="Charting Issue">

<Tip>
  If none of the issue templates suit your inquiry — such as general questions or coding help — please [open a discussion](https://github.com/FunkinCrew/Funkin/discussions) instead of an issue.
</Tip>

### Before You Submit

Complete every step of the Issue Checklist at the top of your chosen template. Issues with incomplete checklists may be closed without review.

Before hitting submit, run through this checklist manually:

- [ ] I am using the latest supported version of the game
- [ ] I am not running any mods (unless the issue involves mods)
- [ ] I am using an official build from Newgrounds or itch.io
- [ ] I searched existing issues and confirmed this hasn't been reported before
- [ ] I am reporting **only one issue** in this submission (split multiple reports into separate issues)
- [ ] My title is clear and concise — not a full description

## Part 3: Pull Requests

Community members are welcome to contribute code, documentation, assets, and more by opening pull requests. This section covers how to structure them for the best chance of acceptance.

### Choosing a Base Branch

Always create a **dedicated branch** in your fork before opening a PR — never work directly on your fork's default `main` branch. That's considered an anti-pattern by GitHub themselves.

Which base branch you target depends on what you're changing:

| Change type | Base branch |
|---|---|
| Game code (`.hx` files) or any other file type | `develop` |
| Documentation (`.md` files) | `main` |
| GitHub files (`.yml`, `.github/` folder) | `main` |

When in doubt, base your branch on `develop`.

### PR Workflow

<Steps>
  <Step title="Fork and branch">
    Fork the [Funkin repository](https://github.com/FunkinCrew/Funkin) and create a new branch from either `develop` or `main` depending on your change type (see the table above). Use a descriptive branch name like `docs/fix-typo` or `fix/minor-bugfix`.
  </Step>
  <Step title="Make your changes">
    Implement your fix, feature, or documentation update. Follow the relevant guidelines in the sections below for code, documentation, or asset PRs.
  </Step>
  <Step title="Open a PR targeting the correct branch">
    Open a pull request back to `FunkinCrew/Funkin` and set the base branch to the same one you branched from — `develop` or `main`.
  </Step>
  <Step title="Respond to review feedback">
    If the team requests changes, your PR will be labelled `status: needs revision`. You have **90 days** to address the requested changes. After that period, the PR will be closed and labelled `status: stale`. You can always request a reopen once the issues are addressed.
  </Step>
  <Step title="Resolve merge conflicts">
    If upstream changes create merge conflicts, update or rebase your branch. Use an [interactive rebase](https://docs.github.com/en/get-started/using-git/about-git-rebase) to squash messy commit histories before requesting re-review.
  </Step>
</Steps>

### Code PRs

Code-based PRs fix bugs or implement new features by modifying `.hx` files inside the `source/` folder.

**Requirements for code PRs:**

- The game must **compile and run** with your changes applied. See the [Compilation Guide](/compiling) if you need help.
- Your code must follow the [Code Style Guide](/contributing/code-style).
- Comments must be meaningful — see the [code comments guidelines](/contributing/code-style#code-comments) for details.

### Documentation PRs

Documentation PRs fix typos or add new information to `.md` files found throughout the repository.

Keep your changes easy to understand and formatted consistently with the surrounding content.

<Warning>
  **Do NOT touch the `LICENSE.md` file** — not even to make small corrections. This file is off-limits for all contributor PRs without exception.
</Warning>

### GitHub PRs

GitHub-related PRs modify `.yml` workflow files or anything inside the `.github/` folder. Test your changes on your fork's own main branch first to make sure you don't break Actions, issue templates, or other automation.

### funkin.assets PRs

The `assets/` submodule lives in a separate repository: [funkin.assets](https://github.com/FunkinCrew/funkin.assets).

- If you **only** modify files in the `assets/` folder, open your PR against `funkin.assets` — not the main `Funkin` repo.
- If your changes touch **both** repositories, open two separate PRs and cross-reference them in each PR's description.
- Always target the `develop` branch in `funkin.assets`, just as you would in the main repo.

#### Charting PRs

Charting PRs adjust chart metadata by modifying `*-metadata.json` files in `preload/data/songs/`.

<Warning>
  The Funkin' Crew **does not accept changes to chart `.json` files** (the actual note data). If you spot an error in a chart, open an issue in the main `Funkin` repo and the team will review and apply fixes themselves.
</Warning>

Charting PRs should only be opened against the `funkin.assets` repository.
