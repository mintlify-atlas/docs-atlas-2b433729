Keeping the codebase consistent makes it easier for everyone — contributors and maintainers alike — to read, review, and debug. This guide covers every style convention used in the FNF repository. If you're submitting a code PR, make sure your changes follow all of these guidelines before opening it.

## IDE Recommendation

<Note>
  **Visual Studio Code is the recommended IDE for FNF development.** It is the only editor with mature tooling for Haxe, and the repository ships with configurations that automate most of the style rules described in this guide.

  Install the following extensions to get the full experience:
  - [`nadako.vshaxe`](https://marketplace.visualstudio.com/items?itemName=nadako.vshaxe) — provides the Haxe Formatter, driven by the repo's `hxformat.json`
  - [`vshaxe.haxe-checkstyle`](https://marketplace.visualstudio.com/items?itemName=vshaxe.haxe-checkstyle) — enforces code quality rules via Haxe Checkstyle
  - [`esbenp.prettier-vscode`](https://marketplace.visualstudio.com/items?itemName=esbenp.prettier-vscode) — handles JSON formatting using the repo's `.prettierrc.js`
  - [`jeremyfa.codedox`](https://marketplace.visualstudio.com/items?itemName=jeremyfa.codedox) — adds IDE support for JavaDoc-style doc comments

  Enable **Format on Save** in your VSCode settings so that `hxformat.json` and Prettier are applied automatically every time you save a file.
</Note>

## Whitespace and Indentation

Indentation style and line-break rules are enforced automatically by the Haxe Formatter extension using the repo's `hxformat.json` configuration file. You don't need to configure anything manually — enabling Format on Save is enough.

The Haxe Checkstyle extension separately monitors `IndentationCharacter` (what character is used) and `Indentation` (how deep the nesting goes), and will surface violations in the Problems panel.

## Variable and Function Names

Name variables and functions using **lowerCamelCase** with descriptive titles. A slightly longer name is always better than a cryptic abbreviation — there is no penalty for verbosity as long as it doesn't become excessive.

```haxe
// Good: descriptive, lowerCamelCase
var targetTimeSteps:Float = 0.0;
var skipEndingTransition:Bool = false;

function changeSection(sections:Int):Void { }
function checkSyncError(?targetTime:Float):Float { }

// Bad: too short to be meaningful
var t:Float = 0.0;
var skip:Bool = false;

function cs(s:Int):Void { }
```

## Code Comments

Comments help future contributors understand _why_ code does what it does — not just what it does. Follow these rules when adding comments:

- Use **JavaDoc-style doc comments** (`/** ... */`) for all `public` functions. The CodeDox extension generates the scaffold automatically.
- Only comment code that **genuinely warrants explanation**. If the code is self-explanatory, skip the comment.
- Keep comments **clear and concise** — don't restate what the code already says.
- Only **sign a comment with your name** if the change is complex enough that future contributors might need to reach out for more context.

## Unused Code

<Warning>
  **Do not comment out unused code.** Leaving commented-out blocks in the codebase makes files longer and harder to navigate for everyone.

  If you need to preserve a snippet for reference, use Git — older code is always recoverable by browsing the commit history. Delete unused code and trust the version control system to keep history safe.

  The `CommentedOutCode` Haxe Checkstyle rule is explicitly enabled in the repo to enforce this.
</Warning>

## License Headers

Do **not** add per-file license headers to source files. The top-level `LICENSE.md` file covers the entire repository. Adding redundant headers to individual files creates maintenance overhead and is inconsistent with the rest of the codebase.

## Imports

All imports should be placed in a **single group** at the top of the file, sorted in **alphabetical order**. The only exception is conditional imports (using compile-time defines), which go at the **end** of the import list — still sorted alphabetically within their block.

```haxe
import haxe.format.JsonParser;
import openfl.Assets;
import openfl.geom.Matrix;
import openfl.geom.Matrix3D;
#if sys
import funkin.io.FileUtil;
import sys.io.File;
#end
```

Do not split imports into multiple groups by module or feature — keep everything in one flat sorted list.

## Argument Formatting

Haxe supports two distinct mechanisms for optional/default function arguments, and they behave differently. **Do not use them together on the same argument.**

| Syntax | Type | Default value | Use when… |
|---|---|---|---|
| `myFunction(?input:Int)` | `Null<Int>` | `null` | You want to detect whether the caller passed a value at all |
| `myFunction(input:Int = 0)` | `Int` | `0` | You always want a concrete fallback and don't need nullability |

Using both (`?input:Int = 0`) is valid Haxe syntax but produces a `Null<Int>` that defaults to `0` — meaning it is never actually `null`, but is still annotated as nullable. This makes null-safety checks noisier and more confusing throughout the codebase.

```haxe
// Good: optional argument — caller can omit it, value will be null
public function checkSyncError(?targetTime:Float):Float

// Good: default argument — always an Int, defaults to 0
function changeSection(sections:Int = 0):Void

// Bad: both together — redundant and misleads the null-safety checker
function changeSection(?sections:Int = 0):Void
```

Choose the form that accurately reflects the intended contract of the argument.

## JSON Formatting

JSON files are formatted automatically by the **Prettier** extension using the repo's `.prettierrc.js` configuration. No manual configuration is required beyond enabling Format on Save.

<Note>
  Prettier will automatically place expressions on a single line if they fit, but will keep them multi-line if they are manually formatted that way.

  - Long single-line objects are automatically expanded.
  - Short multi-line objects are **not** automatically collapsed — you may need to manually remove the first newline in a short multi-line object to convince Prettier to collapse it to one line.
</Note>
